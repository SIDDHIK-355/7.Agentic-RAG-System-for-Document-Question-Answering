Session 7 — Memory & Retrieval: Embeddings, FAISS, and RAG

Personal study notes — covers everything from the live session and hands-on debugging

1. What is RAG?

RAG = Retrieval Augmented Generation

When you ask an LLM something it doesn't know (private documents, your lease agreement, internal company data), RAG lets it find and use that information.

Simple definition: You Retrieve something → Augment (add it to) the prompt → LLM Generates the answer. 
User Query
    ↓
Convert query to a vector (embedding)
    ↓
Search stored document vectors (FAISS)
    ↓
Get the most relevant chunks of text
    ↓
Send chunks + query to the LLM
    ↓
LLM reads the chunks and answers

Why it matters: The LLM's training data doesn't include your private documents. RAG is the bridge.

2. What is an Embedding?

An embedding is a list of numbers (a vector) that represents the meaning of a piece of text.

Model used: nomic-embed-text running locally on Ollama
Output size: Always 768 numbers regardless of input length
Cost: Free — runs on your machine 
"How does AlphaFold work?"  →  [0.21, -0.44, 0.09, 0.77, ...]  ← 768 numbers
"How do proteins fold?"     →  [0.18, -0.41, 0.12, 0.80, ...]  ← very similar!
"What is capital of France?"→  [0.55,  0.12, -0.67, 0.03, ...]  ← very different

The key idea: similar meaning → similar numbers → small angle between vectors.

The model was trained on massive text so it learned that "AlphaFold" and "protein folding" are related. The numbers reflect that relationship.

Why 768 numbers?

Think of it like a point in 768-dimensional space. 2 numbers = a point on a map (x, y). 3 numbers = a point in a room (x, y, z). 768 numbers = a point in a very high-dimensional space where similar meanings cluster together.

Important rule: Once you build your index with one embedding model (e.g. nomic), you must ALWAYS use the same model for queries. Mixing models = meaningless results. Sir's words: "Once you get married to a model, you're married to it."

Session 7 uses dense only. Hybrid retrieval comes in Session 8.

BM25

BM25 = Best Matching function number 25. A keyword search algorithm. It finds documents where your search terms appear frequently and are unique. Good for: product IDs, car numbers, technical codes, names.

4. FAISS

FAISS = Facebook AI Similarity Search

A library that stores vectors and searches them extremely fast. Sir used it since 2017. Facebook/Instagram runs on FAISS. It can search 100 million vectors in under 100ms.

FAISS only stores vectors (numbers). It does NOT store text.
Your app keeps the text separately and uses the IDs FAISS returns to fetch it.

Three files on disk (Session 7)

FileWhat it stores
state/memory.jsonOriginal text of every memory item
state/index.faissThe actual vectors (768 numbers per item)
state/index_ids.jsonList of memory IDs in same order as FAISS positions

Delete all three = agent forgets everything. Keep them = agent remembers across restarts.

How FAISS search works

FAISS stores:
  position 0  →  [0.21, -0.11, 0.87, ...]   ← chunk 1 vector
  position 1  →  [0.05,  0.72, -0.31, ...]   ← chunk 2 vector
  position 2  →  [-0.44, 0.18, 0.09, ...]   ← chunk 3 vector

Query comes in:
  [0.19, -0.10, 0.85, ...]   ← query vector

FAISS returns:
  position 0 matched (score: 0.94)  ← closest!

Your app:
  index_ids.json[0] → "mem:abc123"
  memory.json["mem:abc123"] → original text

5. Chunking

An embedding model returns 768 numbers for any input — whether it's 1 word or 10,000 words. Longer input = more averaged out = less precise search.

Solution: Split documents into smaller pieces (chunks) before embedding.

Session 7 chunking strategy:
Chunk size = 400 words
Overlap = 80 words (so sentences that cross chunk boundaries are preserved)

Sir calls this "the dumbest possible chunking" — Session 8 introduces smarter semantic chunking. 
Document (1200 words):
  [words 1-400]    ← chunk 1
  [words 320-720]  ← chunk 2  (starts 80 words before chunk 1 ended)
  [words 640-1040] ← chunk 3
  [words 960-1200] ← chunk 4

The 80-word overlap is like a TV show coming back from a commercial break 1 minute before where it left off — so you don't lose context at the boundaries.

6. The Agent Architecture (4 Roles)

User Query ↓ MEMORY → reads stored facts, searches FAISS for relevant items ↓ PERCEPTION → understands what needs to be done, creates goal list ↓ DECISION → picks which tool to use OR gives the final answer ↓ ACTION → runs the tool (index, search, fetch URL, etc.) ↓ MEMORY → stores the result ↓ (loop back to MEMORY for next iteration)

Each role's job

RoleJobCan it name tools?
MemoryStore and retrieve informationNo
PerceptionUnderstand the query, maintain goal listNo — never!
DecisionPick tools, synthesize answersYes — this is its job
ActionExecute tool calls, no intelligenceN/A
Key architectural rule — Separation of Concerns:
Perception must NEVER know tool names. If Perception says "use index_document", it is doing Decision's job. This breaks the architecture.

Sir tested this by doing a grep on perception.py: zero MCP tool names should appear in the SYSTEM prompt.

Where tool instructions live

In the tool's own docstring. When Decision reads the available tools, it reads those instructions right there. The guidance travels with the tool, not with Perception.

The two new MCP tools

index_document(path)
Reads a file → cuts into chunks → embeds each chunk → saves into Memory + FAISS
Use when: you want content to be searchable across future turns/runs

search_knowledge(query, k)
Converts query to vector → FAISS searches → returns top k matching chunks
Use when: content is already indexed and you need to retrieve it

8. How Query E Worked (Step by Step)

Query: "Index the file papers/attention.md and tell me what the three key contributions of the Transformer architecture are according to this paper."

iter 1:
  Perception → goal 1: index the file
               goal 2: extract contributions
               goal 3: tell the answer

  Decision → calls index_document("papers/attention.md")

  Inside index_document:
    - reads attention.md (10,492 bytes)
    - splits into 3 chunks (400 words each)
    - chunk 1 → HTTP POST /v1/embed → Ollama → [0.21, ...] → saved to FAISS
    - chunk 2 → HTTP POST /v1/embed → Ollama → [0.05, ...] → saved to FAISS
    - chunk 3 → HTTP POST /v1/embed → Ollama → [-0.44, ...] → saved to FAISS
    - original text of each chunk saved to memory.json

iter 2:
  Perception → goal 1: ✓ done
               goal 2: not done
               goal 3: not done

  Decision → calls search_knowledge("three key contributions of Transformer", k=3)

  Inside search_knowledge:
    - query → HTTP POST /v1/embed → Ollama → [0.19, -0.42, ...] (query vector)
    - FAISS searches 3 stored vectors
    - finds chunk 1 as closest match
    - returns the original text of that chunk (300 chars inline)

iter 3-4:
  Decision → reads the chunk text from history
           → synthesizes answer from what it sees

iter 5:
  Perception → all 3 goals ✓ done
  Agent stops
Key insight: "Three key contributions" as a phrase never appears in the paper. But the embedding model understood the meaning and matched it to the correct chunk. That's the whole point of dense retrieval.

9. Memory Read Path (Vector First)

memory.read(query)
    ↓
Embed the query via gateway (Ollama)
    ↓
FAISS.search(query_vector, k=8)
    ↓
Any hits? → YES → return ranked items
         → NO  → fall back to keyword search over memory.json

The keyword fallback exists for cold starts or when Ollama is unavailable. Once any embeddings exist, vector search dominates.

12. Diagnostic Discipline (When Something Goes Wrong)

Sir's rule: Before adding any fix, ask "What did the role actually see?"

StepWhat to do
1Save the full trace from the iteration that failed
2Identify which role failed (Perception, Decision, Action, Memory)
3Reconstruct exactly what that role saw — read the code that builds its prompt
4Was the role's output rational given what it saw?
5YES → bug is in rendering/upstream. NO → bug is in role's SYSTEM prompt
Real example from Session 7 (Decision looping on search_knowledge):

Wrong fix: add a rule "don't call the same tool twice"
Real cause: _format_hits was dropping result_preview (strings >200 chars excluded from compact dict). Decision literally could not see the search results.
Right fix: render result_preview explicitly in _format_hits.
