Query F — Cross-run Document Recall (FAISS Persistence)

What this query tests: Can the agent index 5 papers in Run 1, then in a completely fresh process (Run 2), answer from the saved FAISS index without re-indexing anything?

The Query

Run 1: "Index every .md file under papers/. Confirm how many chunks were indexed in total."

Run 2: "Across the papers I have indexed, what do they say about chain-of-thought reasoning?"

Run 1 — What Happened (10 iterations)

iter 1 — Discover what files exist

Decision → list_dir("papers/")
Result → Found 5 files: attention.md, cot.md, dpo.md, lora.md, react.md

The agent didn't know what was in the folder. It asked list_dir first to discover the files. This is the "discovery goal" pattern.

iter 2 — First answer attempt (incomplete)

Decision → ANSWER: listed the 5 files
Perception → chunk count goal still not done → keeps going

Decision answered the file listing part but Perception saw the chunk count goal was still open, so the loop continued.

iter 3 — Perception adds 4 new goals + indexes cot.md

Perception → Added 4 new goals — one per remaining paper (cot, dpo, lora, react)
Decision → index_document("papers/cot.md")
Ollama embeds → 3 chunks × POST /v1/embed = 3 vectors saved to FAISS

This is the "append after discovery" mechanism. Once Perception saw the file list, it created one goal per paper and added them to the goal list.

iter 4 — Wrong chunk count answer

Decision → ANSWER: "9 chunks" (wrong — counted attention.md twice)
Perception → marked count goal done but remaining paper goals still open

iter 5 — Indexes dpo.md

Decision → index_document("papers/dpo.md")
Ollama → 3 more chunks embedded and saved

iter 6 — Indexes lora.md

Decision → index_document("papers/lora.md")
Ollama → 3 more chunks embedded and saved

iter 7 — Indexes react.md

Decision → index_document("papers/react.md")
Ollama → 3 more chunks embedded and saved

iter 8 — Confused about react.md

Decision → ANSWER: "react.md was already done"
Perception → count goal still open → keeps going

iter 9 — Correct final answer

Decision → ANSWER: 15 chunks total
— attention.md: 3 chunks
— cot.md: 3 chunks
— dpo.md: 3 chunks
— lora.md: 3 chunks
— react.md: 3 chunks

iter 10 — All done

Perception → ✓ All 8 goals satisfied. Agent stops.

What's on Disk After Run 1

state/
  memory.json      ← text of all memory items (facts, tool outcomes, etc.)
  index.faiss      ← 15 vectors at 768 dimensions each (Ollama made these)
  index_ids.json   ← ["mem:abc1", "mem:abc2", ...] — 15 IDs in order
This is the key point of Query F. The FAISS index is saved to disk. When Run 2 starts as a completely fresh Python process with no in-memory state, it reads these files from disk on the very first iteration. It doesn't need to re-index anything.

Run 2 — Fresh Process, Same Index

Query: "Across the papers I have indexed, what do they say about chain-of-thought reasoning?"

What makes this special: Run 2 starts with zero in-process memory. No knowledge of Run 1's work. But memory.json + index.faiss are still on disk. On iter 1, memory.read embeds the query via Ollama and FAISS instantly finds relevant chunks — without touching any paper files again.

What Run 2 should do (3 iterations)

iter 1 → memory.read embeds "chain-of-thought reasoning" via Ollama
FAISS searches 15 vectors → finds cot.md chunks as most similar
Perception sees indexed corpus in memory hits → creates search + synthesis goals
iter 2 → Decision calls search_knowledge("chain-of-thought reasoning")
Returns chunks from cot.md (and possibly other papers that mention it)
iter 3 → Decision synthesizes answer from the chunks
All goals done. Agent stops.

Zero tool calls to fetch or re-index any files. Everything comes from the persisted FAISS index.

How Indexing Worked (Every iter, Same Pattern)

index_document("papers/cot.md")
        ↓
Read cot.md text (full content)
        ↓
Split into chunks:
  chunk 1: words 1–400
  chunk 2: words 320–720   ← 80 word overlap with chunk 1
  chunk 3: words 640–end
        ↓
For each chunk:
  HTTP POST http://localhost:8107/v1/embed   ← send chunk text to gateway
       ↓
  Ollama (nomic-embed-text) → [0.21, -0.44, ...] ← 768 numbers
       ↓
  Save 768 numbers to index.faiss
  Save original text to memory.json
  Save chunk ID to index_ids.json
        ↓
Return: { chunks_indexed: 3 }

Why Ollama Made This Run Smoothly

Previous runs (Gemini embed)This run (Ollama embed)
Every embed call burned Gemini RPMEvery embed call is free and local
503 errors after 3-4 iterationsAll embed calls returned 200 OK
Competed with chat calls for quotaNo competition — Ollama is unlimited
5 papers × 3 chunks = 15 Gemini calls0 Gemini embed calls used
Lesson: For RAG, always run the embedding model locally (Ollama). Only use cloud APIs for the LLM chat calls (Gemini, Groq, etc.). Mixing both on the same cloud provider exhausts quotas 2x faster.

The Architectural Point

Query F proves one thing: the FAISS index on disk is the medium that crosses the process boundary.

Run 1 (process A):
  indexes 5 papers → writes to disk
  process ends

Run 2 (process B):
  starts fresh, no memory of Run 1
  reads index.faiss from disk on iter 1
  answers from indexed corpus
  never touches the .md files

This is what makes the agent durable. It doesn't matter if you restart your computer, close the terminal, or wait a week. As long as the 3 state files exist, the agent remembers everything it indexed.
